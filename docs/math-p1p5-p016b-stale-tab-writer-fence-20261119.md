## Proposed behavior, off until an explicit cutover

`supabase/candidates/math_p1p5_p016b_writer_contract_v1_dormant.sql` adds two independent nullable settings to the *existing* feature row: `writer_min_jwt_iat` (signed JWT issue-time floor) and `writer_client_contract` (expected browser writer protocol). **Both default NULL = OFF**, and the candidate has no `UPDATE` of the feature row.

Server-side mutation guards execute after the existing owner/Core selection guard, with strict function signature/source, `SECURITY DEFINER`, `search_path` and ACL checks. The JWT time is verified by PostgREST-signed request claims. The allowed SDK `x-client-info` header retains the existing SDK identity and adds `iclub.math/math-p1p5-p016b-v1` only to individual Mathematics Exam Prep PostgREST requests, not to the shared Supabase client or other subjects. No custom CORS header is introduced. **This is a spoofable old-browser compatibility marker, not a security credential; it does not replace signed JWT, per-user ownership, authorization or RLS.**

When a real cutoff is later activated, older signed JWTs and honest old cached JS with a newly refreshed JWT are rejected **before** the guarded write. Existing P1/P5 session IDs, idempotency keys, submitted objective answers, written correctness unknown, verified progress, Practice, Tours and certificates are not rewritten. An old tab can still view saved projections without initiating a rebuild. For the new client, a stale error triggers RU/UZ/EN clear guidance and a non-destructive user-directed answer-copy notice; there is no automatic reload, storage write, retry, or grade assignment. When the learner explicitly chooses Refresh, the client first calls Supabase Auth `refreshSession()` and reloads only after receiving a fresh signed access token. A plain page reload could otherwise reuse the pre-cutover valid JWT and loop on the writer epoch rejection. If session refresh fails, the exact draft remains visible and copyable, and the learner is not signed out. If the assessment host already replaced the form with a loading screen, the notice copies only the exact rejected response payload kept in memory (written response, numeric/text input, MCQ selection number, or Extra Hard explanation). Profile data, tokens and unrelated RPC arguments are excluded. The MCQ option number alone is not proof that an answer was saved or can be resubmitted after randomized options; users must verify their session after refreshing.

**Unsent answers in already-running historical JS cannot be retroactively copied by code that was not loaded in that browser tab.** Before any live cutoff, an independently reviewed change-management strategy must validate old-client pending-answer UX and a safe learner communication window. The source package does not claim this risk has disappeared.
