# Rules Maintenance v1 — jteshaboev1984-ops/iClub_APP

**Status:** предложение для docs-only PR; вступает в силу после отдельного одобрения владельца и слияния с `main`. Не меняет приложение или опубликованные материалы.

## Источники и границы

- Постоянный [Rules Inbox](https://github.com/jteshaboev1984-ops/iClub_APP/issues/570) — первичный журнал решений, **не** task tracker.
- Действующий реестр: [Реестр обратной связи](ICLUB_FEEDBACK_TO_RULES_REGISTER_2026-11-18.md).
- Утверждённые предметные/продуктовые спецификации, `AGENTS.md`, `docs/ops/CHAT_PROTOCOL.md`, Issue/PR с последними комментариями и точным SHA имеют приоритет над датированными заметками.
- Новые записи отсчитывать с момента создания Inbox; старый register — исходная историческая база. Не копировать всю историю обратно.
- Никаких изменений банка, scoring, доступа учеников, live Supabase, тарифов или production.

## Шаг 1: регистрация после решения

В рамках разрешённой рабочей задачи при **явно подтверждённом владельцем** новом постоянном правиле или важном конфликте добавить **один комментарий** в Inbox:
```text
RULE-CANDIDATE
source: <проверяемый URL исходного решения>
decision: <одно короткое решение, не фантазировать>
scope: <предмет/модуль/жанр/весь проект>
kind: confirmed-rule | scoped-rule | conflict | pending-hypothesis
owner_approval: <URL + дата, иначе "not confirmed">
checks: <как проверять>
```
Записывать источник как ссылку, не копировать приватные тексты, имена детей или ключи ответов. Если инициатор не давал однозначного подтверждения и нет ссылки на решение, отметить гипотезу или запросить решение владельца, но не объявлять правило CONFIRMED. **Разовая задача, факт приёмки одного кадра/вопроса и обычный баг — в свой рабочий Issue/PR, не в Inbox.** Не откладывать регистрацию до еженедельного запуска. При ошибке GitHub прямо сообщить, что фиксация не состоялась.

## Шаг 2: периодическая проверка

Проверка на основании **всех** GitHub Issue comments, в том числе при необходимости всех страниц; нельзя ограничиваться несколькими последними и говорить, что журнал пуст.

Использовать GitHub comment ID (`comments/{id}`) как устойчивый идентификатор. Искать уже связанные открытые Draft PR и проверенные записи `RULES-REVIEW` в Inbox. Не открывать второй PR на те же ID. Если слияние не произошло, запись не обработана окончательно.

Для новых сообщений классифицировать `CONFIRMED` / scoped / one-off / historical / `DERIVED_PENDING` / conflict; проверять повторы, утверждённые действующие правила и область действия. Короткие инструкции менять **только** если меняется сам процесс чатов. Реестр — если появились действительно новые доказательные записи. `AGENTS.md` — только для постоянного действующего правила. Предметный контракт — лишь при согласованной корректировке. Никакого массового переоформления из-за старых статусных дат.

Если реальных новых решений нет — не создавать PR и не менять файлы. Если GitHub недоступен, сообщить об ошибке; это **не** результат "нет изменений".

Если требуется изменение — подготовить один отдельный docs-only Draft PR от актуального `main`, с таблицей `source comment ID → подтверждение → старая/новая формулировка → файл → проверка`. Любые конфликты с текущим PR owner-решением, никаких силовых слияний.

## Шаг 3: завершение с защитой от дублей

До слияния запись имеет статус `PROPOSED`; не отмечать `APPLIED`. После **проверенного** слияния, и только после него, комментарием в Inbox указать:
```text
RULES-REVIEW
state: APPLIED
source_comment_ids: <ID, ID>
merged_pr: <URL>
main_sha: <SHA>
classification: <для каждого ID: тип + правило/реестр>
```
Для отклонённых и требующих подтверждения записей использовать `REJECTED` или `PENDING_OWNER` с обоснованием, не выдавать это за установленное правило. Если PR закрыли без слияния, снова рассматривать исходные IDs на следующем цикле. Не требуется отдельная БД, JSON ledger или новый сервис.

## Периодичность и ответственность

Предлагаемый цикл: еженедельно. В первом цикле месяца дополнительно проверять противоречия, дубли и устаревшие статусные указания **только** в правилах, без переаудита приложения. Запуск возможен вручную или через **реально созданную** ChatGPT Automation с доступом к GitHub; расписание само по себе не доказывает доступность коннектора или успешность записи. Итоговая проверка первого автоматического запуска обязательна.

Рабочие чаты фиксируют одобренные правила в Inbox; обслуживающий аудит классифицирует их. Только владелец разрешает слияние в `main`, изменение ChatGPT Project Settings или release. GitHub merge никогда не обновляет настройки ChatGPT автоматически.
