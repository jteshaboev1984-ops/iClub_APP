# AI Tutor — сохранение истории: изолированный owner-gated контракт (DRAFT)

**Статус: инженерный кандидат / не включён / не утверждена политика хранения / не опубликовано.**
Канонический Issue: [#412](https://github.com/jteshaboev1984-ops/iClub_APP/issues/412).
Основание: скриншот пользователя после повторного открытия Telegram WebApp от 21.11.2026.
Это исправление не относится к предметным достижениям, проверке заданий, тарифам или расширению платной генерации.

## 1. Что реально установлено

В текущем `iclub-ai-v21-ui.js` переписка хранится в `state.threads = new Map()`; `appendMessage` ограничивает активную ветку 40 сообщениями и ничего не записывает на сервер. Закрытие WebView уничтожает Map. Восстановить более ранние утраченные сообщения из этого Map технически нельзя. Авторский скриншот подтверждает два видимых UZ ответа и потерю истории после закрытия.

В репозитории есть исторический файл `20261006133000_iclub_global_ai_conversation_ui_v1.sql`, но он **прямо указывает, что текст диалога не хранится**. Не считать его готовым механизмом истории. Опубликованный `practice_rules` и одна реальная успешная General Help генерация подтверждены отдельно; новая история не должна повторно звать модель при открытии приложения.

## 2. Что подготовлено в этом Draft PR

- `supabase/candidates/iclub_ai_tutor_history_v1_owner_gated_dormant.sql`: **не миграция**, не выполняется автоматически. Изолированный механизм `private` для маленькой истории. Контроль **`enabled=false`**; действующее AI beta-consent **не означает** согласия на хранение переписки.
- `private.iclub_ai_tutor_history_v1_optins`: отдельное явное согласие пользователя на хранение; прекращение согласия удаляет **только свою** кандидатную историю.
- `private.iclub_ai_tutor_history_v1_messages`: owner + thread + request UUID + speaker + locale + text + expiration. Индекс уникальности делает повторную доставку идемпотентной. Таблица RLS-on и закрыта для прямого `anon`/`authenticated`/`service_role` доступа.
- `public.iclub_ai_tutor_history_service_v1`: сервер получает идентичность **из `auth.uid()` и роли подписанного вызова**, а не из запрашиваемого `user_id`. `status`, `opt_in`, `append`, `read`, `opt_out`. Требует текущую допущенную бета-учётную запись, отдельное согласие и отсутствие активной защищённой проверки. `opt_out` работает даже после отключения функции оператором.
- До 40 сообщений на одну ветку; не более 25 активных веток; текст до 2400 символов; RU/UZ/EN; первоначальный **кандидат** срока видимости 24 часа, с проверкой истечения при чтении. Это **не утверждённый срок хранения**. Для физического удаления подготовлена операция `private.iclub_ai_tutor_history_purge_expired_v1()`, закрытая от пользователей; **автоматического cron пока нет**.
- Блокируются ветки `practice_attempt_*`, `exam_prep*`, `tour_*`, `qa_*`. Это **только кандидат для общих продуктовых переписок**, не для персонального разбора Practice, оплаченных/сгенерированных ответов, академических материалов или ответов на проверочные задания. Нельзя переиспользовать данные в качестве авторитетного источника AI, оценки или progress.
- `supabase/tests/iclub_ai_tutor_history_v1_isolated.sql` + узкий PG17 workflow: проверка default-OFF, явного согласия, доступа только владельца, разных аккаунтов, отклонения защищённого контекста, повторных UUID, удаления и отсутствия изменения синтетического Core.

**Ничего из этого пока не подключено к текущему `iclub-ai-v21-ui.js`. Это преднамеренно:** до утверждения приватности добавлять сохранение текста учеников в production нельзя; отсутствие UI-изменений также не ломает действующую beta. Срок 24 часа — инженерная гипотеза для проверок, не постоянное правило.

## 3. Незакрытые решения владельца до реализации и публикации

1. **Состав истории:** только готовая публичная справка (минимальная бета) или также обычные свободные вопросы модели; для персонального Practice и академических вопросов — отдельное решение с учётом источников и действующего PC4 24h answer-text cleanup. Нельзя копировать защищённые ответы из PC4 в долго живущую историю.
2. **Хранение и прозрачность:** длительность хранения, явное предупреждение и согласие (включая несовершеннолетних), порядок удаления/очистки и срок в резервных копиях. Кандидат 24 часа **не утверждён**.
3. **Модель записи:** клиентская история не является доказательством ответа модели (клиент может менять локально представленный текст); нужна явная provenance-маркировка. Определить, разрешено ли хранить произвольный текст пользователя и ответы, а также какие классы исключить.
4. **Публикация:** отдельное разрешение на версионированную миграцию/cron/контроль включения, затем на UI и production. Никогда не вводить живые таблицы или сохранять сообщения по одному общему «работай».

## 4. Следующий пакет после согласования продукта

1. Без переписывания общего Tutor сделать клиентский адаптер к RPC (только для разрешённого класса сообщений). При успешной генерации сохранять видимую пару с исходным UUID и версией источника, а не повторно запускать provider при восстановлении.
2. По авторизованному `status` после входа восстанавливать только собственную ветку; при logout/account-switch и защищённом экране очищать DOM и удерживать показ до серверной проверки. Обработать out-of-order async ответы, потерянные ACK, повторный вход, локаль и ограничение 40 сообщений.
3. Добавить независимое **подлинное** signed GoTrue/JWT → HTTP/PostgREST → PostgreSQL 17 тестирование двух пользователей, logout, cross-owner, denied RPC, protected quiz; Chromium mobile reload/resume RU/UZ/EN. Текущий SQL fixture устанавливает claims в изолированной БД и **НЕ подтверждает криптографическую проверку JWT**.
4. Публиковать только после отдельного GO и независимого review; затем проверить готовность Vercel, сохранение после полного закрытия Telegram WebApp и 0 новых платных вызовов на read. Не восстанавливать ранее потерянные сообщения из финансовых журналов.
